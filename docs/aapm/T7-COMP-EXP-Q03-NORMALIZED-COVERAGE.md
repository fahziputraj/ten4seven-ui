## 3. Normalization method

NORMALIZED — each meaningful corpus name was assigned exactly one disposition
from the Q03 vocabulary:

1. resolve exact normalized matches to the current canonical component
   registry, retaining aliases as aliases;
2. fold case, ampersand/and spelling, punctuation, dash variants, apostrophe
   variants, and repeated whitespace;
3. collapse obvious intent, size, color, state, density, and presentation
   adjectives into a component variant or preset;
4. collapse repeated component names and spelling variants into an alias;
5. classify hero, public-shell, and admin compositions as blocks or recipes
   unless a reusable generic interaction contract is proven;
6. classify product, Farm, SaaS, ERP, finance, logistics, marketing, and
   workflow nouns as domain compositions unless a generic API is proven;
7. defer rich editors, spreadsheets, advanced grids, scheduling, maps,
   diagrams, whiteboards, canvas, media engines, resizable/drag engines, and
   other dependency-heavy surfaces;
8. reject a candidate as a new canonical component when the corpus gives no
   distinct public typed API, interaction semantics, accessibility model, and
   multi-surface reusable value.

The unique canonical test is therefore stronger than “the name is different”:

    distinct user intent
      + distinct interaction semantics
      + reusable public typed API
      + explicit accessibility model
      + multi-surface reusable value
      = legitimate canonical candidate

The result is a planning classification, not permission to implement. A
candidate remains non-canonical until its API, state, accessibility,
responsive, motion, token, source, example, and acceptance contracts are
approved in the queue assigned below.
